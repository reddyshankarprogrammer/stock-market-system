Quantiva · quantiva.ai · product and technology plan

A trading journal and trading platform our users will want to open every day

This plan takes our existing Java microservices to a full product in the class of TraderSync and TradeZella: a polished web app, a landing page that shows every feature in short video clips, modern sign-in, a settings module, five subscription plans, an admin portal with a revenue dashboard, and AI coaching on top of each trader's own history. A day-by-day schedule starts on 23 October 2026.

Owner Shanker Reddy Updated 23 October 2026 Proposal: nothing implemented yet

Where we are

The backend is further along than most products at this stage. What is missing is everything a user sees.

Already built

  • 7 Spring Boot services behind an API gateway, with Kafka, MySQL and Redis
  • account-service: multi-broker accounts, trades, holdings, fees, taxes, dividends, performance
  • Broker statement import for Groww, Zerodha, Binance and Exness
  • K3s production setup with GitHub Actions and Argo CD
  • ai-service folder, Dockerfile and Kubernetes manifests ready for a Python service

Gaps to close

  • No frontend and no landing page
  • No refresh tokens, no Google sign-in, no email verification
  • Market prices are simulated for six US stocks; no real price history or candles
  • No journal features yet: notes, tags, screenshots, playbooks
  • user-service is still on Spring Boot 3; the rest are on Boot 4

How the pieces connect

flowchart LR
  U[Browser or mobile app] --> W[Next.js web app]
  W -->|session cookie| G[API gateway]
  U -. sign in .-> K[Keycloak]
  K -. Google sign-in .-> GO[Google]
  K -. verification email .-> E[Email provider]
  G -->|X-User-Id, X-User-Role| S[Java services]
  G --> J[journal-service, new]
  G --> A[ai-service, Python]
  A --> C[Claude API]
  A --> KR[Kronos-small, self-hosted]
  S --- KF[(Kafka)]

The browser never holds raw tokens. The gateway keeps them in a server-side session stored in Redis and gives the browser an httpOnly cookie. The gateway checks Keycloak's signed tokens instead of today's shared JWT_SECRET, and the services keep receiving X-User-Id and X-User-Role as they do now.

Page order

  • Hero with headline, one call to action and the dashboard clip
  • Feature clips (above), then animated statistics counters
  • Supported brokers. Use broker logos only with each broker's permission.
  • Security section: passkeys, two-factor codes, data stays in our own cluster
  • Pricing, FAQ, final call to action

How we make and serve the clips

  • Remotion renders clips from React code, so they match the real UI and can be re-rendered after each redesign. Its free license covers individuals and very small companies; a company license is likely needed.
  • Screen Studio or Playwright recordings for quick real captures. Rive or Lottie for small animated icons.
  • WebM (AV1) with an MP4 fallback, autoplay muted and looping, a still poster frame first, loaded only when scrolled into view, served from a CDN.
  • Respect the browser's reduce-motion setting by showing the poster frame instead of the clip.

Login options

Standard

  1. Email ID and password.
  2. Remember me keeps the session longer on this device.
  3. Forgot password by email link.
  4. Authenticator code as a second step for trading and money actions.

Social

  1. Google, Microsoft and GitHub first.
  2. Apple and LinkedIn when their developer approvals arrive.
  3. Accounts link by verified email, so nobody gets two accounts.
  4. Apple's rules require "Sign in with Apple" in the iOS app once any social login is offered.

Future: biometric

  1. Passkeys from phase 1: fingerprint, face or device PIN, phishing-proof.
  2. Face ID and fingerprint work through passkeys on supporting devices, and natively in the Expo app (phase 7).
About a custom app PIN. Passkeys give the same one-tap login and cannot be phished, so we recommend them first. If we also offer a 4–6 digit app PIN, it must be set up after a full login on that device, work on that device only, and lock after about five wrong attempts. A PIN alone must never place trades, move money, or change the password or email; those always ask for the password or passkey again.

Risks and compliance

  • Personal data. Email, mobile, gender and country fall under India's DPDP Act. We need consent text, a privacy policy and a deletion process. The mobile number is collected without verification, so it cannot be trusted for recovery or alerts yet.
  • Payments and tax. Subscriptions need a payment provider agreement, GST or VAT handling and refund rules.
  • Social login. Apple, LinkedIn, Microsoft, GitHub and Google each have their own app review and terms; plan lead time.
  • Admin portal. The most privileged area: authenticator-code login, IP allow-list or VPN, and every action audited.
  • Trading and advice. Live trading, or AI output that reads as a buy or sell signal, may fall under SEBI rules. Keep AI labelled as educational until legal review.
  • Market data. Forecasts and replay need real historical prices. Simulated data makes both meaningless.
  • Third-party AI. Sending trade history to an external API needs to be disclosed to users.
  • Brand assets. Broker logos and names only with permission.
